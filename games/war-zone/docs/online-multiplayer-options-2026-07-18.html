技術調査レポート / 2026-07-18 / 対象: GitHub Pages上のCanvas 2Dアクションゲーム

無料で簡単なオンライン対戦方式を比較する

現行PeerJS実装の失敗原因を確認し、P2P、TURN、マネージド対戦SDK、WebSocketリレー、権威サーバー、BaaS、自前Nodeサーバーを「簡単さ・無料枠・接続性・公平性・将来性」で比較した。

TL;DR

無料で実現できる。ただし、最短案と最終形は違う。
まず2台で遊べる状態を最小改修で作るなら 現行PeerJS + Cloudflare TURN。バックエンドをほぼ作らず8人まで試すなら Playroom Kit。公開後も育て、ホスト離脱や不正を減らす本命は Cloudflare Durable Objects + PartyServer である。
最小改修

PeerJS + TURN

現在のホスト権威ロジックを残す。TURN資格情報用の小さなWorkerと、連番・再接続を追加する。

最短SDK

Playroom Kit

ルームと同期をSDKへ任せられ、在室中の計画的なホスト移譲APIもある。無料は1日10ユニークユーザーなので、8人テストには合うが一般公開には小さい。

本命

Durable Objects

1ルームを1つのサーバー状態として実装。全員が入力だけを送り、移動・命中・AI・スコアはサーバーが決める。

結論

1. 主結論

現段階では、「PeerJS + Cloudflare TURNで接続を成立させる」→「必要性が確認できたらDurable Objectsへ権威ロジックを移す」という二段階が、変更量と将来性のバランスが最もよい。

2. その理由

現行コードはすでにホストがゲーム全体を計算し、参加者が入力を送り、ホストがスナップショットを返す構造になっている。問題の第一層はTURN不在などの接続性、第二層は連番・再接続・予測不足、第三層はブラウザホスト依存である。最初から第三層まで全て作り直すと、オンライン対戦が必要かを検証する前に大きな移植が発生する。

3. 実装判断への含意

  • 友人2〜8人、ホスト退出で終了してよい: PeerJS + TURN、またはPlayroom。
  • ランキング・公平性・ホスト退出後の継続が必要: Durable Objectsによるサーバー権威。
  • 普通のNode.jsサーバーとして学びたい: Colyseus OSS + Render Free。
  • Firebase/Supabaseはロビー、参加者一覧、戦績保存には使えるが、試合の20〜30Hz通信には使わない。

4. 結論が変わる条件

1日10人以下でバックエンドを絶対に書きたくないならPlayroomが第一候補になる。毎日複数の8人部屋が長時間動くならDurable Objects無料枠は足りなくなり、固定費のNodeホストまたは有料ゲーム基盤が上位になる。ターン制へ変わるならFirebase/Supabaseも有力になる。

5. 確信度

高い。 無料枠とサービス制約は2026-07-18時点の公式情報で確認した。実際の遅延と必要帯域だけは、スナップショットサイズ、参加地域、端末性能で変わるため、2台・別回線の計測が必要である。

調査質問と前提

質問: GitHub Pagesのフロントエンドを維持し、最大8人程度の小規模な2Dアクション対戦を、個人開発で無料枠・少ない運用負担の範囲に収める最適方式は何か。

  • GitHub PagesはHTML/CSS/JavaScriptの静的配信を担当し続ける。
  • ゲームサーバーまたは中継サービスは別ドメインでよい。
  • 現状はクライアント入力30Hz、ホスト状態送信20Hz。
  • 「無料」は、無料枠を超えなければ月額0円であること。開発限定無料は公開運用の無料とは区別する。

GitHub Pagesが静的ホスティングであること自体は問題ではない。ブラウザから外部のWSS/WebRTC/SDKへ接続できる。ただしGitHub Pagesだけで常駐WebSocketサーバーを動かすことはできない。GitHub Pages公式説明

分析

現行実装で確認できた弱点と、有力な失敗要因

  1. TURNが設定されていない。 PeerJSの既定ICE設定はSTUNだけで、対称NATや厳しいファイアウォール同士では直接接続できない。PeerJS自身もこの場合はTURNが必要と説明しており、有力な接続失敗要因である。ただし今回の失敗がTURN不足だったと確定するには、PeerJS error、ICE connection state、選択candidate pairを記録して切り分ける必要がある。PeerJS FAQ
  2. 共有PeerJS Cloudへ依存している。 シグナリングは無料だが共有サービスであり、手動IDは他利用者と衝突し得る。PeerJS Cloud
  3. スナップショットにtick/seqがない。 現状はreliable: falseで接続し、20Hzの全状態をそのまま適用する。古い状態の破棄、入力ACK、欠落検知がない。
  4. ホストのゲームループがブラウザ描画に結び付いている。 requestAnimationFrameでシミュレーションしているため、ホストが別タブへ移動、最小化、端末スリープすると更新が遅延・停止し得る。
  5. 再接続と再参加がない。 一時切断がそのまま試合離脱になり、同じ席と状態へ戻れない。
  6. 現在位置の補間だけで、ローカル予測・サーバー照合がない。 参加者は入力の往復を待つため、ホストより体感が不利になる。
GitHub Pagesは原因ではない。原因は、静的ページの外側に必要なシグナリング・TURN・権威サーバー・再接続設計が不足していることにある。

候補1: 現行PeerJS + Cloudflare TURN

最も少ない変更で別回線間の接続成功率を上げる。Cloudflare Realtime TURNは最初の1,000GB/月が無料で、その後はエグレス1GBあたり$0.05。小規模な座標同期なら収まる可能性は高いが、現行snapshot bytesを計測して確認する。Cloudflare Realtime料金

ただしTURN長期キーをGitHub Pagesへ置いてはいけない。小さなWorkerから有効期限付き資格情報を発行し、ブラウザには短期資格情報だけを渡す。資格情報の無断発行で無料枠を消費されないよう、短いTTL、Origin/ルームトークン検査、発行レート制限、利用量アラートも必要である。TURN資格情報の公式手順

最低限追加するもの

  • Cloudflare TURNを含むiceServers。
  • 入力にinputSeq、状態にserverTickとlastProcessedInputSeq。
  • 古いスナップショットの破棄、重要イベントの重複排除。
  • 接続段階、ping、タイムアウト、再接続トークン。
  • ホストがバックグラウンドへ移ったら警告し、必要なら試合を一時停止。

反対理由: ホスト離脱、ホスト0ms優位、ホスト改造による不正は残る。これは接続性の修理であり、公平性の修理ではない。

候補2: Playroom Kit

ルーム、参加者、共有状態、マッチメイキングを自前サーバーなしで使える。公式にはシューター例があり、ホストがスポーンやダメージ計算を担当する構成が示されている。Playroomシューター例

無料枠は1日10ユニークユーザー、カード不要、APIキー不要。8人対戦を1回試す用途には合うが、一般公開するとすぐ上限へ達する。Liteは月$10から。Playroom料金

Nugget: 「無料で一番簡単」の答えは、一般公開ではなく少人数の動作確認に限ればPlayroomである。ただしtransferHost()は現在のホストが在室中の対象へ明示的に渡すAPIであり、突然切断後の自動移譲や完全状態移送を保証するものではない。突然離脱時の選出と状態継承は実機検証が必要。transferHost

候補3: WebSocketリレー

参加者 ─入力→ WSSリレー ─入力→ ホストブラウザ
参加者 ←状態─ WSSリレー ←状態─ ホストブラウザ

NAT/TURNを避けながら、今のホスト計算を残せる。PartyKitはJavaScriptでルームサーバーを書け、Individualは無料、最大10プロジェクト、保存は24時間ごとに消去される。試合状態が一時的なら消去自体は問題にならない。PartyKit公式

Render Freeへ小さなNode WebSocketリレーを置く案もある。無料の750インスタンス時間/月はワークスペース全体で共有する。アクティブなWebSocketメッセージがある間は停止せず、15分無通信だと停止し、次回起動は約1分かかる。無料サービスは任意に再起動され得るため、試合中断を許容する試作向け。帯域等を超えた場合、支払い方法がなければ停止し、登録済みなら追加請求の可能性がある。Render Free / Render WebSocket

反対理由: 中央リレーを置いてもホスト権威なら、ホスト退出・不正・遅延格差は残る。

WebSocket共通の限界: WebSocketはTCP上の順序付き・信頼配送なので、損失時には古い位置データの再送待ちで新しいsnapshotも遅れる。カジュアルな2D対戦ではまず実測して許容判断できるが、モバイル回線で高いtwitch性を求める場合は、unreliable/unorderedなWebRTC DataChannelやWebTransport対応基盤を再評価する。RFC 6455

候補4: Cloudflare Durable Objects + PartyServer

1つのルームコードを1つのDurable Objectへ対応させる。Durable Objectは単一地点で順序付けされた状態を持ち、複数WebSocketを調整でき、公式にもマルチプレイヤー用途が挙げられている。Durable Objects概要

GitHub Pages上の各ブラウザ
        │  入力 {seq, buttons, aim}
        ▼
Workerルーター ─→ Room Durable Object
                    ├─ 30Hz固定シミュレーション
                    ├─ 移動・命中・AI・スコア判定
                    └─ 15〜20Hz snapshot/delta配信
        ▲
        │  {serverTick, ackSeq, stateDelta}
        └────────────────────────────

PartyServerはCloudflare公式系のライブラリで、ルームルーティング、接続ライフサイクル、ブロードキャストをDurable Objects上に簡潔に実装できる。Cloudflare PartyKit/PartyServerリポジトリ

無料枠の現実的な試算

無料枠は100,000 request相当/日、13,000 GB-s/日。受信WebSocketメッセージは20通で1 request相当、送信WebSocketメッセージは無料である。無料枠超過後は該当操作が失敗し、追加請求は発生しない。Durable Objects料金

人数各人の入力頻度request相当/秒100,000枠での合計ルーム時間/日
2人30Hz3約9.26時間
8人30Hz12約2.31時間
8人15Hz6約4.63時間
8人10Hz4約6.94時間

Duration側は128MB割り当てとして約28.2アクティブルーム時間/日なので、高頻度入力では受信メッセージ枠が先に尽きる。いずれも入力メッセージだけを数えた理論上限で、接続確立、Workerルーティング、制御メッセージ、再接続、ロビー通信を含まない。また複数ルーム合計の値である。入力変化時送信、照準量子化、50〜100msバッチ、ローカル予測が重要になる。

Hibernationは待機ロビーには有効だが、固定ゲームループ中はタイマーと継続処理があるため試合中の節約には使いにくい。デプロイやランタイム再起動でメモリ内の試合状態自体が失われる場合、Socket再接続と完全snapshotだけでは復旧できない。数秒ごとのcheckpointと重要event logを保存するか、「サーバー再起動時は試合終了」と仕様化する必要がある。保存頻度を上げるほどSQLite書き込み枠と実装量が増える。Durable Objects WebSocketガイド

候補5: Colyseus OSS + Render Free

ColyseusはNode.js/TypeScript向けのゲームサーバーフレームワークで、サーバーだけが状態を変更し、差分をクライアントへ同期する。ルーム、マッチメイキング、再接続の土台を自作しなくてよい。ブラウザ向けSDKはCDN読込にも対応する。Colyseus状態同期

本体は無料でセルフホスト可能だが、公式Managed Cloudは月$15からで無料ではない。Render Freeなら月額0円で試せる一方、コールドスタート、任意再起動、単一インスタンス、帯域制約を受ける。Colyseus料金

向く条件: Durable Objects固有の実行・課金モデルを避け、普通のNodeゲームループとして権威サーバーを学びたい場合。

候補6: Photon Realtime

部屋、マッチメイキング、リージョン選択、イベント中継がゲーム向けに用意され、JavaScriptを含む複数SDKがある。Photon Realtime概要

ただしRealtime無料枠は20 CCU・60GB/月で「Development Only」。PhotonにはFusion/Quantum向けの商用可能な100 CCU無料枠もあるが、Unity等との深い統合を前提とし、今回のplain JavaScriptゲームへは直接適用しにくい。またPublic Cloudのイベント中継だけではゲーム判定はサーバー権威にならない。Photon自身も高速ゲームでMaster Clientへ依存する方式よりカスタムサーバー側コードを推奨している。Photon料金 / ホスト移譲の注意

候補7: Supabase / Firebase

Supabase Realtime無料枠は2Mメッセージ/月、100メッセージ/秒、200接続。Broadcastは送信1通と購読者ごとの受信を全て数える。8人部屋で1人のホストが他7人へ15Hzで状態を配るだけでも (送信1 + 受信7) × 15 = 120メッセージ/秒 となり、参加者からホストへの入力を加える前に無料レート上限を超える。Supabase制限 / メッセージ計算法

Firebase Realtime DatabaseのSpark無料枠は同時100接続、1GB保存、10GB/月ダウンロード。ただしデータベース同期であり、移動・弾道・AIを継続計算する権威ゲームサーバーではない。Firebase料金 / RTDB制限

結論: Supabase/Firebaseを位置・弾・敵状態の20〜30Hz同期に使わない。ルーム一覧、Ready、チャット、戦績、ターン制だけに使う。

推奨ロードマップ

  1. 接続性の検証: まずPeerJS error、ICE state、candidate pairを表示し、家庭回線↔スマートフォン回線で2台テスト。その結果に基づきTURNを追加する。
  2. ネットコードの安定化: 入力ACK、古い状態破棄、再接続、100ms補間バッファ、ローカル予測を追加。
  3. ゲームコア分離: Canvas、DOM、音声から、移動・射撃・衝突・AI・スコアの純粋ロジックを分ける。固定30Hzとseed付き乱数を使う。
  4. 権威サーバー試作: まず1マップ・2人だけをPartyServer/Durable Objectへ移し、クライアントは入力だけ送る。
  5. 8人負荷試験: 10/15/30Hz入力、15/20Hz状態配信でrequest数、snapshot bytes、RTT、補間品質を比較。

方式に関係なく必要なプロトコル

  • protocolVersion、roomId、playerId、sessionToken。
  • 入力のseq、サーバーのtick、最後に処理した入力のackSeq。
  • 最大8人、payloadサイズ上限、入力頻度上限、数値範囲と型の検証。
  • イベントと連続状態の分離。発砲・リロード・参加退出はイベント、位置・向きは最新状態。
  • 自分は予測と照合、他人は補間。切断後は15〜30秒の同じ席への再参加。
  • GitHub PagesのOrigin検査、短期ルームトークン、秘密鍵をブラウザへ置かない。

未解決点・実機で埋めるギャップ

  • 現行スナップショットの平均・最大バイト数。弾、犬、戦車、拾得物の数で大きく変動する。
  • 参加者の地域。Durable Objectは最初に作られた場所に寄るため、国内対戦と大陸間対戦で結果が変わる。
  • Playroom無料枠超過時の具体的な拒否挙動と、現行の大きな全状態配信での実測。
  • ホストタブを背景化したときの実測停止時間。
  • 求める公平性。友人戦ならホスト権威で十分だが、ランキングを付けるなら不十分。

外部視点として、サービス横断調査、アーキテクチャ分類、Durable Objectsへの反証レビューを独立に実施し、結論の順位が反転する条件を確認した。
